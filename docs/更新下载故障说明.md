# 更新清单下载失败

## 现象与排查结论

Windows 1.0.0 用户反馈：检查更新时，`update-manifest-windows-x64.json` 请求尝试两次后失败，但浏览器可以手动下载。

这个路径表明故障发生在更新清单下载阶段，尚未下载 ZIP 或替换文件。旧版更新器复用了答题专用的 `RetryingSession`，该会话强制直连，会忽略系统及环境代理。因此浏览器与更新器可能使用不同网络路径。该代码问题已确认；仅凭这条反馈，无法确定用户 Windows 上是否还存在 TLS、CDN 或其他网络故障。

## 修复行为

- 更新器使用独立会话，先尝试可发现的系统或环境代理，再尝试 GitHub 直连；不读取 `.netrc` 认证信息。
- 更新器排除获取 Token 期间占用的本机 8888 端口代理。答题请求继续使用原来的强制直连机制。
- GitHub 版本 API 只走官方地址。取得可信预期哈希后，清单、安装包和源码文件可以依次尝试 GH-Proxy、GHFast 备用线路。
- 每份备用文件都必须匹配预期哈希；缺少 GitHub 清单摘要时，该清单不会走第三方线路。
- 单条线路失败后切换下一条，次数有限；断流会重新下载当前文件，失败或取消时清理临时下载，不替换本地程序。
- 页面区分“检查更新失败”和“更新准备失败”，错误包含资源阶段、线路及错误类型，不输出代理凭据或签名 URL。

代理发现不等于完整复用浏览器网络栈；依赖 PAC 脚本的代理配置可能仍需显式代理环境变量。

## 验证与旧版升级

离线回归覆盖代理可用但直连失败、代理失败后的直连、清单断流及备用下载、哈希不匹配、大小限制、取消清理、CDN 跳转时保留代理和认证隔离。完整测试共 263 项，261 项通过，2 项平台相关测试跳过。

本机真实读取了 GitHub v1.1.1 发布信息及清单，校验成功并生成 Windows 更新计划；没有下载完整安装包或应用更新。这不等于已在反馈问题的 Windows 机器上复测。

已安装的 1.0.0 可执行文件不会因源码修改自动获得修复。需要手动安装包含修复的 1.1.2 或更新版本，之后才能使用新的更新下载逻辑。
